# Vendor App — ระบบจัดหาที่ทำงานบนข้อมูลจริงจาก Epicor

FastAPI (Swagger) + Next.js (JavaScript) + MongoDB + เข้าสู่ระบบด้วย Microsoft Entra ID

## แหล่งข้อมูล — อ่านตรงนี้ก่อน

ระบบนี้ **ไม่ได้เก็บข้อมูลผู้ขาย/สินค้าเอง** แต่อ่านจากฐานข้อมูล `epicor_procurement`
ที่สคริปต์ ETL ของโปรเจกต์ **epicorExploreData** ดึงมาจาก Epicor ERPPRD

```
Epicor ERPPRD (SQL Server)
      │  scripts\04_etl_to_mongodb.py
      ▼
MongoDB: epicor_procurement
      ├─ vendors           ผู้ขาย            ~1,959    ← ETL เป็นเจ้าของ (แอปอ่านอย่างเดียว)
      ├─ items             สินค้า            ~8,620    ← ETL เป็นเจ้าของ
      ├─ item_last_price   ประวัติราคา       ~8,619    ← ETL เป็นเจ้าของ
      ├─ transactions      PO/รับของ/บิล   ~195,000    ← ETL เป็นเจ้าของ
      ├─ etl_runs          ประวัติการรัน               ← ETL เป็นเจ้าของ
      ├─ deliveries        งวดส่งของ        ~49,290    ← ETL ขั้นที่ 5 เป็นเจ้าของ
      ├─ vendor_delivery   สรุป OTD ผู้ขาย   ~1,036    ← ETL ขั้นที่ 5 เป็นเจ้าของ
      │
      ├─ app_users         ผู้ใช้ของแอป                ← แอปเป็นเจ้าของ
      ├─ rfqs              ใบขอราคา                    ← แอปเป็นเจ้าของ
      ├─ rfq_invites       ผู้ขายที่เชิญ + token portal  ← แอปเป็นเจ้าของ
      ├─ rfq_quotes        ใบเสนอราคาที่ได้รับ          ← แอปเป็นเจ้าของ
      ├─ app_vendor_items  ราคาที่ชนะ RFQ               ← แอปเป็นเจ้าของ
      ├─ app_vendor_notes  โน้ต/สถานะอนุมัติภายใน       ← แอปเป็นเจ้าของ
      ├─ app_counters      เลขที่เอกสาร                 ← แอปเป็นเจ้าของ
      └─ app_audit_logs    บันทึกการประกาศผู้ชนะ        ← แอปเป็นเจ้าของ
```

**กติกาสำคัญ:** collection ของแอปทุกตัวขึ้นต้นด้วย `app_` หรือ `rfq_` โดยตั้งใจ
เพราะ ETL รันแบบ "ล้างแล้วโหลดใหม่" — ถ้าแอปไปใช้ชื่อ `items` หรือ `vendors` ซ้ำ
ข้อมูล RFQ และผู้ใช้จะหายทุกครั้งที่รัน ETL

ถ้าเปิดเว็บแล้วไม่มีข้อมูล ให้รัน ETL ก่อน:

```cmd
cd C:\Users\praewrung.p\Desktop\epicorExploreData
python scripts\04_etl_to_mongodb.py            :: ผู้ขาย สินค้า ราคา รายการเคลื่อนไหว
python scripts\05_delivery_performance.py --to-mongo   :: การส่งตรงเวลา
```

> ขั้นที่ 5 ต้องใส่ `--to-mongo` ด้วย ไม่งั้นได้แค่ไฟล์ Excel/CSV และหน้าเว็บจะไม่มีข้อมูล
> ความตรงเวลา (ส่วนอื่นยังใช้ได้ปกติ)

backend จะเตือนใน log ตอน startup เองด้วยถ้าฐานข้อมูลยังว่าง และ `/api/health`
จะคืน `etl_ready: false` พร้อมข้อความบอกว่าต้องทำอะไร

## หน้าจอ

### ค้นหาสินค้า — `/products`

เปิดมาเห็นรายการทันที เรียงตามมูลค่าที่เคยซื้อจริง ไม่ต้องพิมพ์อะไรก่อน

ช่องค้นหา **ไม่ต้องพิมพ์ให้ตรงเป๊ะ**:

| พิมพ์ | ได้อะไร |
|---|---|
| `010160204008` | เจอ `01-016-02-04-008` — ระบบยอมให้มีตัวคั่นแทรก |
| `ethernet switch` | ตรงคำในคำอธิบาย |
| `switch moxa` | ทุกคำต้องเจอ แต่เจอคนละที่ได้ (คำอธิบาย + ชื่อผู้ขาย) |
| `ethernett swich` | สะกดผิด — ระบบหาคำที่ใกล้เคียงให้ พร้อมบอกว่าใช้คำไหนแทน |

ทุกแถวแสดง **ราคาล่าสุด · ซื้อล่าสุดเมื่อไร · ราคาถูกสุดที่เคยได้ · จำนวนผู้ขาย · ยอดซื้อรวม**
และมีปุ่มขอใบเสนอราคาในแถวเลย

การให้คะแนนความตรง: รหัสตรงเป๊ะ > รหัสขึ้นต้นด้วยคำค้น > คำขึ้นต้นในคำอธิบาย >
เจอที่ไหนก็ได้ แล้วบวกแต้มตามมูลค่าที่เคยซื้อ (มีเพดาน) เพื่อให้ของที่ใช้จริงลอยขึ้นก่อน

### รายละเอียดสินค้า — `/products/<รหัส>`

ตอบสามคำถามในหน้าเดียว:

1. **ตอนนี้ราคาเท่าไร** — การ์ดราคาล่าสุด / ถูกสุด / แพงสุด พร้อมวันที่ ผู้ขาย และเลข PO
2. **ใครขายได้บ้าง** — ตารางผู้ขายทุกรายที่เคยขายรหัสนี้ให้เรา เรียงจากราคาล่าสุดถูกสุด
   ติ๊กเลือกแล้วกดขอใบเสนอราคาได้ทันที
3. **ที่ผ่านมาซื้อยังไง** — กราฟราคาย้อนหลัง + ตาราง transaction จริงทุกใบ
   แยกแท็บ ใบสั่งซื้อ / รับของ / ใบแจ้งหนี้

ถ้าครั้งล่าสุดซื้อจากเจ้าที่ไม่ใช่เจ้าที่ถูกที่สุด ระบบจะขึ้นแถบเตือนให้เห็นทันที

### ผู้ขาย — `/vendors`

ตารางปกติ (ไม่ใช่ grid) ค้นด้วยชื่อ รหัสผู้ขาย เลขผู้เสียภาษี ชื่อผู้ติดต่อ หรืออีเมล
เปิดเข้าไปเห็นข้อมูลบริษัทและผู้ติดต่อก่อน แล้วสลับแท็บดูสินค้าที่เคยขายให้เรา
(พร้อม**ราคาล่าสุดของรายนั้นโดยเฉพาะ**) และรายการเคลื่อนไหวทั้งหมด

### ความตรงเวลาในการส่ง — อยู่ในทุกจุดที่ต้องตัดสินใจ

ราคาถูกที่สุดไม่ได้แปลว่าคุ้มที่สุด ถ้าของมาช้าจนงานสะดุด ระบบจึงวางตัวเลข
**ความตรงเวลา (OTD)** ไว้ข้าง ๆ ราคาทุกที่ที่ต้องเลือกผู้ขาย:

| ที่ไหน | เห็นอะไร |
|---|---|
| หน้าสินค้า | ตารางผู้ขายมีทั้ง **ราคาล่าสุด · OTD รวม · OTD เฉพาะสินค้ารหัสนี้** |
| รายชื่อผู้ขาย | คอลัมน์ OTD + ตัวกรอง "เฉพาะรายที่ส่งตรงเวลาต่ำกว่า 70%" |
| หน้าผู้ขาย | การ์ด OTD + แท็บ **การส่งตรงเวลา** ดูรายงวด กรองเฉพาะที่ช้า/ค้างส่ง/เคยเลื่อนกำหนด |
| ตารางเทียบราคา RFQ | OTD ใต้ยอดรวมของผู้ขายแต่ละคอลัมน์ + เตือนถ้าเจ้าถูกสุดคือเจ้าที่ส่งช้า |
| ผู้ขายที่ระบบแนะนำ | OTD ประกอบการเลือกว่าจะเชิญใคร |
| หน้าภาพรวม | OTD ทั้งบริษัท · ผู้ขายที่ควรตามงาน · งวดที่ค้างส่งนานที่สุด |
| **ตามงานส่งของ** `/deliveries` | หน้าเฉพาะสำหรับไล่ดูว่างวดไหนช้า ของใคร เป็นของอะไร |

### ตามงานส่งของ — `/deliveries`

หน้าผู้ขายดูได้ทีละราย ส่วนหน้านี้กวาดข้ามผู้ขายทั้งหมดในที่เดียว เลือกดูได้ 5 มุม:
**ยังค้างส่ง · ส่งช้ากว่ากำหนด · ส่งตรงเวลา/ก่อนกำหนด · เคยเลื่อนกำหนด · ทุกงวด**
แล้วสลับได้สองมุมมอง:

- **รายผู้ขาย** — ใครค้างเยอะสุด กดแถวเพื่อกางดูของจริงที่ค้างอยู่ (สินค้า เลข PO งวดที่ กี่วัน มูลค่า)
  พร้อม OTD รวมของรายนั้น เพื่อดูว่าครั้งนี้ผิดปกติหรือเป็นนิสัย
- **รายงวด** — ทุกงวดเรียงจากหนักสุด ไล่ตามทีละรายการได้เลย

ค้นด้วยชื่อผู้ขาย รหัส/ชื่อสินค้า หรือเลข PO และกรองตามความช้าได้ (เกิน 7 / 30 / 90 วัน)

หัวคอลัมน์และคำอธิบายเปลี่ยนตามมุมที่ดู — มุมส่งตรงเวลาจะอ่านว่า “เร็ว 5 วัน”
ไม่ใช่ “-5 วัน” เพราะเลขติดลบลอย ๆ อ่านผิดเป็นช้าได้ง่าย

**สิ่งที่ตั้งใจกันไม่ให้ตัวเลขหลอกตา** (ตาม `docs/delivery_date.md` ข้อ 7)

- ผู้ขายที่มีงวดน้อยกว่า 5 งวด ติดป้าย **"ข้อมูลน้อย"** ไม่เอา 100% จาก 2 งวด
  ไปเทียบกับ 92% จาก 200 งวด และการจัดอันดับบนหน้าภาพรวมตัดรายเหล่านี้ออก
- **งวดที่ยังไม่ส่งไม่ถูกนับใน %** ผู้ขายที่ดองงานไว้จึงอาจได้ OTD สวยเกินจริง —
  ระบบแสดง **จำนวนงวดค้างส่ง** คู่กับ % เสมอ และขึ้นแถบเตือนในหน้าผู้ขาย
- แสดง **มัธยฐาน** คู่กับค่าเฉลี่ย เพราะงวดที่ช้าเป็นปีไม่กี่งวดดึงค่าเฉลี่ยเพี้ยนได้ง่าย
- งวดที่ **เคยเลื่อนกำหนด** ติดป้ายไว้ พร้อมบอกว่าช้ากี่วันเมื่อเทียบกำหนดเดิม
- บอกด้วยว่าวันกำหนดมาจาก **ผู้ขายรับปาก** (`PromiseDt`) หรือ **ค่าในระบบ** (`DueDate`)
- เตือนไว้ในหน้าจอว่าวันรับของคือวันที่คลังคีย์เข้าระบบ ช้า 1-3 วันอาจเป็นเรื่อง
  กระบวนการภายใน ไม่ใช่ความผิดผู้ขาย

ตอนประกาศผู้ชนะ ระบบบันทึก **OTD ณ วันที่ตัดสิน** ไว้ในผลด้วย เพื่อให้ย้อนดูได้ว่า
ตอนนั้นรู้อะไรบ้าง

### ประมาณราคา BOM — `/boms`

เอา BOM ของโครงการมาตีงบเบื้องต้นจาก **ราคาที่บริษัทเคยซื้อจริง** ก่อนจะไปขอราคาผู้ขาย

1. **นำเข้า** — อัปโหลด Excel/CSV หรือวางข้อความจาก Excel ตรง ๆ
   ระบบหาคอลัมน์ชื่อรายการ / จำนวน / หน่วย / รหัส จากหัวตารางให้เอง
   ไม่มีหัวตารางก็เดาจากรูปแบบได้ · **แสดงผลที่อ่านได้ให้ตรวจก่อนเสมอ ไม่บันทึกทันที**

   ทนกับ BOM ที่ไม่ได้จัดมาให้: ข้ามหัวเอกสารที่อยู่เหนือหัวตาราง (ชื่อโครงการ/ผู้จัดทำ/วันที่)
   ข้ามหัวข้อหมวดที่ไม่มีจำนวน และอ่าน "1,200" เป็น 1200 ไม่ใช่ 1
   มีไฟล์ตัวอย่างไว้ลองที่ `samples\`
2. **จับคู่** — จับรายการใน BOM เข้ากับสินค้าใน Epicor แล้วดึงราคาซื้อล่าสุดมาคิด
3. **หน้าวัสดุรายตัว** — กดที่แถวไหนก็ได้ เข้าหน้า `/boms/<id>/lines/<no>` (เป็นหน้าเต็ม
   ไม่ใช่กล่องซ้อน) มีสองแท็บที่สลับไปมาได้ และแท็บผูกกับ URL จึงเปิดแยกแท็บเบราว์เซอร์
   หรือแชร์ลิงก์ได้:

   - **จับคู่วัสดุ** — ค้นหาสินค้าใกล้เคียง เปลี่ยนรหัสที่จับคู่ แก้จำนวน
     หรือกรอกราคาเองเมื่อของนั้นไม่มีในระบบ · **ติ๊กได้ทีละ 1 รหัสเท่านั้น**
     เพราะหนึ่งบรรทัดใน BOM ผูกกับสินค้าได้รหัสเดียว
   - **เทียบราคาจากผู้ขาย** — เฉพาะของชิ้นนี้ เทียบราคาที่แต่ละเจ้าเสนอมา
     กับ **ราคาที่บริษัทเคยจ่ายให้เจ้านั้นจริง** สำหรับรหัสนี้ (`เคยซื้อจากเจ้านี้`)
     จึงตอบได้ว่ารอบนี้ถูกลงหรือแพงขึ้นจากเดิม ไม่ใช่แค่เทียบกันเองในรอบนี้ ·
     ท้ายแท็บนี้มีกล่อง **"ขอราคาเพิ่มสำหรับรายการนี้"** (ดูหัวข้อถัดไป)
4. **ต่อยอด** — ออกใบขอราคา (RFQ) หรือโหลดงบเป็น Excel

**ออกใบขอราคาโดยเลือกผู้ขายรายรายการ** — เลือกผู้ขายของแต่ละรายการได้อิสระ
แล้วเลือกวิธีรวมใบได้ 2 แบบ (เห็นจำนวนใบเปลี่ยนทันทีก่อนกด):

- **ผู้ขายหนึ่งรายได้ใบเดียว** (ค่าตั้งต้น) — เจ้าที่ขายหลายรายการในโครงการนี้
  จะได้ใบเดียวที่มีของครบทุกชิ้นที่เลือกเขาไว้ ฝั่งเขาตอบง่ายกว่า ฝั่งเราตามน้อยกว่า
  และแต่ละใบมีเฉพาะของที่เจ้านั้นขายจริง ไม่ใช่ทั้ง BOM
- **หนึ่งรายการหนึ่งใบ** — แยกใบตามสินค้า ใช้เมื่ออยากเทียบราคาของแต่ละชิ้นแยกกันชัด ๆ

(ยังมีปุ่ม "ออกใบรวมทั้งใบ" ไว้สำหรับกรณีที่ผู้ขายชุดเดียวกันขายได้ทั้งใบ)

ผู้ขายที่ให้เลือกไม่ได้มาจากการเดา — เป็นเจ้าที่ **เคยขายรหัสนั้นให้เราจริง** แนบ
ราคาล่าสุดของเจ้านั้นและสถิติการส่งตรงเวลามาให้ดูก่อนตัดสินใจ (ทั้งภาพรวมและเฉพาะรหัสนี้)
งานนี้อยู่ที่ **หน้าเต็ม** `/boms/<id>/rfq` ไม่ใช่กล่องซ้อน — ต้องกวาดตาดูหลายรายการ
เทียบราคากับสถิติส่งของแล้วค่อยตัดสินใจ กล่องซ้อนบีบพื้นที่ และกดพลาดนอกกล่องทีเดียว
งานที่เลือกไว้หายหมด · ปุ่มออกใบอยู่ในแถบที่ติดขอบล่าง เลื่อนดูยาวแค่ไหนก็ไม่หนี

**ดูทีละรายการ** — สารบัญด้านซ้ายบอกว่ามีกี่รายการ อยู่ตรงไหน และรายการไหนยังไม่ได้
เลือกผู้ขาย กดข้ามไปรายการไหนก็ได้ หรือกดถัดไป/ก่อนหน้าทีละรายการ
(กองทุกรายการต่อกันยาว ๆ อ่านยากและเลื่อนพลาดง่าย)

**ค้นหาผู้ขายเพิ่มเองได้ 2 ทาง** ถ้ารายชื่อที่ระบบให้มายังไม่พอ:

- **ตามอุปกรณ์ที่ใกล้เคียง** (ค่าตั้งต้น) — ใช้เมื่อไม่รู้ว่าใครขายของแบบนี้
  ระบบค้นสินค้าที่คล้ายกันก่อน แล้วคืนผู้ขายที่เคยขายของพวกนั้น
  **พร้อมบอกว่ามาจากสินค้าตัวไหนและเคยขายราคาเท่าไร** — ตรวจย้อนกลับได้ ไม่ใช่คำแนะนำลอย ๆ
- **ตามชื่อผู้ขาย** — ใช้เมื่อรู้อยู่แล้วว่าจะเชิญเจ้าไหน ค้นจากชื่อ รหัส หรืออีเมล

ผู้ขายที่เพิ่มเองจะติดป้าย **"เพิ่มเอง · ไม่เคยขายรหัสนี้"** ไว้ชัด ๆ
เพราะช่องราคาที่ว่างของเขาจะถูกอ่านผิดเป็น "ยังไม่เคยเก็บราคา" ได้ง่าย

### ขอราคาเพิ่มทีหลัง — จากหน้าวัสดุรายตัว

คำถามว่า *"ควรถามใครเพิ่มไหม"* เกิดตอนเห็นราคาที่ได้มาแล้ว ไม่ใช่ตอนเริ่มโครงการ —
ได้ราคามา 2 เจ้าแล้วรู้สึกว่าแพง ก็ควรถามเพิ่มได้จากตรงนั้นเลย กล่องนี้จึงอยู่
**ท้ายแท็บเทียบราคา** ของหน้าวัสดุ (`/boms/<id>/lines/<no>?tab=compare`)
ไม่ต้องย้อนกลับไปหน้าออกใบของทั้งโครงการ

- ใบที่ออกจากตรงนี้เป็น **ใบละหนึ่งผู้ขาย** และมีเฉพาะของชิ้นนี้ชิ้นเดียว
- ออกได้แม้ยังไม่เคยออกใบเลย — รายการที่ยังไม่มีราคาจะเห็นกล่องนี้แทนตารางเปล่า
- ค้นหาผู้ขายเพิ่มได้จากตรงนี้ ทั้งตามชื่อและตามอุปกรณ์ที่ใกล้เคียง (ตัวเดียวกับหน้าออกใบ)
- ออกเสร็จแล้วหัวรายการกับป้ายสถานะอัปเดตเอง ไม่ต้องรีเฟรช

**ไม่ส่งซ้ำไปหาเจ้าเดิมโดยไม่รู้ตัว** — ผู้ขายที่เคยถูกเชิญสำหรับบรรทัดนี้จะติดป้าย
`เชิญแล้ว · RFQ-xxxx` ให้เห็นก่อนกด และถ้าติ๊กเจ้านั้นซ้ำจะมีขั้นยืนยันโผล่มา
ถ้าไม่ยืนยัน ระบบตัดเจ้านั้นออกให้แล้วรายงานว่าตัดใครออกเพราะอะไร

ที่ไม่ห้ามตายไปเลย เพราะการถามซ้ำมีเหตุผลจริง — ราคาที่เสนอมาหมดอายุ
หรือเปลี่ยนรหัสที่จับคู่ใหม่แล้วต้องขอราคาของใหม่ · กติกาคือ **ต้องเป็นการตั้งใจกด
ไม่ใช่ผลข้างเคียงของการกดออกใบรอบสอง**

> ธง "เชิญแล้ว" อ่านจาก `rfq_invites` เสมอ ไม่ใช่จาก `vendor_key` ที่จดไว้ที่บรรทัด —
> ใบที่ออกแบบรวมผู้ขายหลายเจ้าไว้ในใบเดียวจะไม่มี `vendor_key` ติดมากับบรรทัด
> ถ้าเชื่อค่าที่จดไว้อย่างเดียวจะสรุปว่า "ยังไม่เคยเชิญ" ทั้งที่เชิญไปแล้ว

### เทียบราคา — ดูเป็นรายสินค้า ไม่ใช่รายผู้ขาย

`/boms/<id>/compare` — ใบขอราคาออกเป็นใบต่อผู้ขาย (เขาจะได้ตอบครั้งเดียวจบ)
แต่ตอนตัดสินใจ คำถามคือ **"ของชิ้นนี้ ใครให้ราคาดีที่สุด"** ไม่ใช่ "ใบไหนถูกสุด" —
เปิดทีละใบจึงเทียบอะไรไม่ได้เลย เพราะใบหนึ่งมีผู้ขายเจ้าเดียว

หน้านี้รวมราคาจากทุกใบของโครงการกลับมาเรียงเป็น **แถวละสินค้า คอลัมน์ละผู้ขาย**
ไฮไลต์ราคาต่ำสุดของแต่ละแถว เทียบกับงบที่ตั้งไว้ และสรุปว่า
"ถ้าเลือกเจ้าถูกสุดของแต่ละชิ้น จะจ่ายรวมเท่าไร ต่างจากงบกี่ %"

**ช่องว่างสามแบบถูกแยกให้ชัด** — ไม่ได้เชิญ / เชิญแล้วยังไม่ตอบ / ตอบแล้วแต่ไม่เสนอรายการนี้
ถ้าแสดงเป็นขีดเหมือนกันหมด คนอ่านจะสรุปผิดว่า "เจ้านี้ไม่มีของ"

**เลือกผู้ชนะได้จากหน้านี้เลย** — ติ๊กทีละแถวแล้วกดอนุมัติทีเดียว ระบบจะไปประกาศผลใน
ใบขอราคาที่ถูกต้องให้เอง คนเลือกจากสินค้า ไม่ต้องจำว่าของชิ้นนี้อยู่ในใบไหน

> ลำดับช่องในแต่ละแถวถูกบังคับให้ตรงกับลำดับหัวคอลัมน์เสมอ — ถ้าเรียงคนละแบบ
> ราคาของเจ้าหนึ่งจะไปโผล่ใต้ชื่ออีกเจ้าแบบเงียบ ๆ ซึ่งมองไม่เห็นจากหน้าจอ
> และทำให้เลือกผู้ชนะผิดตัว

### ขั้นตอนของงาน — ป้ายสถานะที่อ่านจากของจริง

ทุกรายการใน BOM มีป้ายบอกว่าเดินไปถึงไหนแล้ว และโครงการมีแถบสรุปว่ามีรายการค้างอยู่ขั้นไหน:

| ขั้น | หมายถึง |
|---|---|
| ยังไม่จับคู่ | ยังไม่รู้ว่าเป็นสินค้ารหัสไหน |
| ตีราคาแล้ว | มีราคาแล้ว แต่ยังไม่ออกใบขอราคา |
| ออกใบขอราคาแล้ว | ออกใบแล้ว ยังไม่ได้ส่งให้ผู้ขาย |
| รอผู้ขายเสนอราคา | ส่งไปแล้ว ยังไม่มีใครตอบ |
| ได้รับราคาแล้ว | มีผู้ขายเสนอราคากลับมาแล้ว (บอกจำนวนราย) |
| อนุมัติราคาแล้ว | ประกาศผู้ชนะแล้ว — โชว์ชื่อผู้ชนะ ราคา และต่างจากงบกี่ % |

**ทุกขั้นคำนวณจากสถานะจริงของใบขอราคา ใบเสนอราคาที่เข้ามา และผลประกาศผู้ชนะ**
ไม่ใช่ธงที่คนกดเอง — ธงที่กดเองจะค้างอยู่ที่ค่าเก่าทันทีที่มีคนลืมกด แล้วทั้งกระดานก็เชื่อไม่ได้

หนึ่งรายการอาจอยู่ในใบของผู้ขายหลายเจ้า (ตอนรวมใบตามผู้ขาย) ระบบจะถือ **ขั้นที่ไกลที่สุด**
เป็นสถานะของรายการนั้น — ถ้ามีเจ้าหนึ่งอนุมัติแล้ว ของชิ้นนั้นก็จบจริง ๆ
ต่อให้ใบของอีกเจ้ายังรอตอบอยู่

เมื่ออนุมัติราคาแล้ว หัวโครงการจะสรุป **ราคาที่อนุมัติจริงเทียบกับงบที่ตั้งไว้** ให้เห็นเป็น %
— ตัวเลขนี้คือคำตอบว่าการประมาณงบจากราคาซื้อเก่าแม่นแค่ไหน

ระบบติ๊กไว้ให้ 3 รายที่ราคาถูกที่สุด — เปลี่ยนได้ทั้งหมด · รายการที่ไม่ติ๊กผู้ขายเลยจะไม่ออกใบ
เพราะใบที่ไม่มีใครตอบ ออกไปก็เปล่าประโยชน์ · ออกแล้วบรรทัดใน BOM จะจำเลขใบไว้
กันกดออกซ้ำโดยไม่รู้ตัว

**สามอย่างที่ระบบยืนยันจะบอกเสมอ** เพราะตัวเลขงบที่ดูสะอาดแต่ปิดบังที่มา
อันตรายกว่าตัวเลขที่บอกข้อจำกัดของตัวเอง:

- **จับคู่ผิดแย่กว่าจับคู่ไม่ได้** — คะแนนความมั่นใจต่ำกว่าเกณฑ์ ระบบจะไม่จับคู่ให้
  ปล่อยว่างไว้แล้วบอกให้เลือกเอง
- **ยอดรวมบอกความครอบคลุมคู่กันเสมอ** — "ตีราคาได้ 25/40 รายการ" อยู่ข้างยอดรวมตลอด
  พร้อมคำเตือนว่างบจริงจะสูงกว่านี้
- **เตือนเมื่อหลายรหัสตรงพอ ๆ กันแต่ราคาต่างกันมาก** — ของจริงมีหลายรหัสที่คำอธิบาย
  เหมือนกันเป๊ะแต่ราคาคนละเรื่อง หยิบตัวแรกมาเงียบ ๆ อาจผิดเป็นสิบเท่าโดยไม่มีใครรู้
- ราคาที่เก่ากว่า 1 ปี ติดธงไว้ว่าอาจไม่ใช่ราคาปัจจุบันแล้ว

ตั้ง **% เผื่อสำรอง (contingency)** และ **% VAT** ได้ต่อโครงการ · งานที่ทำไว้เก็บกลับมาเปิดทีหลังได้

### ใบขอราคา (RFQ) — `/rfqs`

ครบเหมือนเดิม แต่ทำงานบนข้อมูลจริง:

1. **สร้าง** — จากหน้าสินค้ากดปุ่มเดียว ไม่ต้อง "เพิ่มสินค้าเข้าระบบ" ก่อนอีกแล้ว
   เพราะ RFQ อ้าง `part_num` ของ Epicor ตรง ๆ
2. **เชิญผู้ขาย** — ระบบแนะนำจากประวัติจริงว่าใครเคยขายรหัสนี้ให้เรา ไม่ใช่การเดาจากหมวด
3. **ส่ง** — ออกไฟล์ Excel ใบขอราคาต่อผู้ขายหนึ่งราย + ลิงก์ portal ให้กรอกราคาออนไลน์
4. **เทียบราคา** — ตารางแถว=สินค้า คอลัมน์=ผู้ขาย ไฮไลต์ราคาต่ำสุด
   และมี **คอลัมน์ "ราคาเดิม"** ให้เห็นทันทีว่าที่เสนอมาถูกลงหรือแพงขึ้นกี่ %
5. **ประกาศผู้ชนะ** — ทั้งใบหรือแยกรายบรรทัด บันทึกส่วนต่างเทียบราคาเดิมไว้ด้วย

ผู้ขายเห็นเฉพาะรายการของตัวเอง — **ไม่เห็นราคาเดิมของเรา และไม่เห็นว่ามีใครถูกเชิญด้วย**

### หน้าเสนอราคาของผู้ขาย — `/portal/<token>`

หน้าที่คนนอกบริษัทเห็น เปิดด้วยลิงก์เฉพาะราย ไม่ต้องล็อกอิน ทำงานเป็น 3 ขั้น
มีแถบบอกว่าอยู่ขั้นไหนแล้ว:

1. **รับทราบเงื่อนไข** — หน้าแรกที่ผู้ขายเห็นมีแค่เงื่อนไขกับช่องติ๊ก
   **ยังไม่แสดงเนื้อหาใบขอราคาเลย** — ไม่มีชื่อสินค้า ไม่มีรหัส ไม่มีจำนวน
   บอกเพียงเลขที่ใบ จำนวนรายการ และกำหนดส่งราคา เพื่อให้รู้ว่าลิงก์นี้คือใบไหน
   ระบบบันทึก **เวลา · ชื่อผู้รับทราบ · เวอร์ชันของเงื่อนไข** ไว้เป็นหลักฐาน

   การกันนี้อยู่ที่ **ฝั่งเซิร์ฟเวอร์** ไม่ใช่แค่ซ่อนบนหน้าจอ — ก่อนกดรับทราบ
   `GET /api/portal/{token}` จะไม่ส่งรายการสินค้าออกไปเลย (เปิด DevTools ดูก็ไม่เห็น)
   และไฟล์ Excel ใบขอราคาก็โหลดไม่ได้ (403) เพราะในไฟล์มีรายการครบ
2. **กรอกราคา หรือแนบไฟล์** — ตารางคำนวณยอดรวมและ VAT ให้ทันที
   และ **แนบไฟล์ใบเสนอราคาตัวจริงได้** (PDF / Excel / Word / รูป / ZIP · ไม่เกิน 20 MB
   ต่อไฟล์ · แนบได้หลายไฟล์ · ลบไฟล์ที่แนบผิดได้)
3. **ส่ง** — แก้ไขและส่งใหม่ได้จนกว่าใบขอราคาจะปิด

แก้ข้อความเงื่อนไขได้ที่ `.env` โดยไม่ต้องแก้โค้ด:

```ini
PORTAL_TERMS_VERSION=1.1
PORTAL_TERMS=ข้อที่หนึ่ง|ข้อที่สอง|ข้อที่สาม
```

> เลื่อน `PORTAL_TERMS_VERSION` ทุกครั้งที่แก้เนื้อหา จะได้ตรวจย้อนหลังได้ว่า
> ผู้ขายแต่ละรายรับทราบเงื่อนไข "ฉบับไหน"

## ตัวอักษรและระยะห่าง

ทั้งระบบใช้สเกลตัวอักษรชุดเดียว ย่อลงจากเดิมประมาณ 10% เพื่อให้เห็นข้อมูลต่อหน้าจอมากขึ้น
และดูโล่งขึ้น:

| ใช้กับ | ขนาด |
|---|---|
| หัวเรื่องบนแถบบน | 16px |
| หัวการ์ด | 14px |
| เนื้อหาทั่วไป / ปุ่ม | 13.5px |
| ตาราง | 12.5px |
| คำอธิบายรอง (`.cell-sub`, `.hint`) | 11.5px |
| ป้ายเล็ก / ตัวพิมพ์ใหญ่ | 11px |

**ไม่ได้ย่อเท่ากันทุกอัน** — ถ้าคูณตัวเลขเดิมด้วยอัตราเดียวแล้วปัดเศษ ขนาดที่กระจุกอยู่
ช่วง 12–15px จะยุบมากองรวมกันจนหัวข้อ เนื้อหา และคำอธิบายมีขนาดเท่ากันหมด
อ่านแล้วไม่รู้ว่าอะไรสำคัญกว่าอะไร จึงใช้ตารางแปลงที่รักษาระยะห่างระหว่างชั้นไว้ทุกคู่

**ตัวเล็กลงแล้วต้องเพิ่มที่ว่างตาม** ไม่งั้นจะแน่นกว่าเดิม — ระยะในการ์ด ตาราง และช่องกรอก
ถูกขยายขึ้นพร้อมกัน (`.card-body` 20→22, แถวตาราง 12/16→14/18, เนื้อหาหน้า 24→28)

**ขั้นต่ำ 11px** เพราะตัวอักษรไทยมีสระบนล่าง เล็กกว่านี้เริ่มอ่านยากจริง —
มีเทสต์คุมไว้ว่าไม่มีข้อความไหนบนหน้าจอเล็กกว่านี้

ทั้งระบบไม่มีสีน้ำเงินแล้ว พื้นหลังเป็นขาว ตัวอักษรเป็นดำ ระดับชั้นต่าง ๆ แยกด้วยเส้นคั่น
และน้ำหนักเทา ไม่ใช่ด้วยสี

| โทเคน | ค่า | ใช้กับ |
|---|---|---|
| `--card` | `#ffffff` | พื้นการ์ด เมนูซ้าย แถบบน |
| `--page` | `#f7f7f7` | พื้นหลังหน้า (อ่อนกว่าการ์ดนิดเดียว พอให้เห็นขอบ) |
| `--cream` | `#f0f0f0` | หัวตาราง ป้าย แถวที่ชี้ค้าง |
| `--border` | `#e0e0e0` | เส้นคั่นทั่วไป |
| `--ink` | `#1a1a1a` | ตัวอักษรหลัก ปุ่มหลัก สีเน้น |
| `--muted` | `#646464` | ข้อความรอง (contrast 5.9:1 บนพื้นขาว) |

ชื่อตัวแปร `--blue` / `--navy` ยังอยู่เพื่อไม่ต้องแก้ทุกไฟล์ แต่ค่าจริงเป็นดำและขาวแล้ว

**สีที่ยังเหลืออยู่คือสีที่แปลว่าอะไรบางอย่าง** — เขียว = ผ่าน/ถูกที่สุด, เหลือง = รอ/ต้องดูเพิ่ม,
แดง = ปัญหา ถ้าตัดออกด้วยจะเหลือแค่ตัวหนังสือให้อ่านทีละบรรทัดว่าอันไหนมีปัญหา
ซึ่งช้ากว่ามากเวลามีของเป็นร้อยแถว

**ของที่เคยแยกกันด้วยสีฟ้า ตอนนี้แยกด้วยรูปแบบแทน:**

- เมนูที่เปิดอยู่ = พื้นเทาอ่อน + แถบดำด้านซ้าย
- ป้าย "ออกใบขอราคาแล้ว" = ขอบดำพื้นขาว, "ได้ราคาแล้ว" = พื้นดำตัวขาว (ไล่จากจางไปเข้มตามความคืบหน้า)
- กราฟราคาย้อนหลัง = ไล่ระดับเทา **บวกลายเส้น** (ทึบ / ประยาว / ประสั้น) เพราะเทาล้วนอย่างเดียว
  แยกไม่ออกเวลาเส้นทับกัน

ข้อยกเว้นเดียวคือโลโก้ Microsoft บนปุ่มเข้าสู่ระบบ ซึ่งแก้สีไม่ได้ตามข้อกำหนดเครื่องหมายการค้า

`frontend/theme_check.mjs` เปิดทุกหน้าจริงแล้วอ่านค่าสีที่เบราว์เซอร์คำนวณออกมา
ถ้ามีสีที่ค่าน้ำเงินสูงกว่าแดง/เขียวเกินเกณฑ์ หรือมีข้อความคู่ไหน contrast ต่ำกว่า WCAG AA
เทสต์จะฟ้อง (ตรวจจากหน้าจอจริง ไม่ใช่ grep ไฟล์ CSS — สีอาจมาจาก inline style หรือตัวแปรก็ได้)

## ความเร็วในการโหลด

สองอย่างที่ทำไว้ให้หน้าเว็บไม่ต้องรอ:

### 1. โครงหน้าขึ้นก่อน ไม่รอข้อมูล

ทุกหน้าวาดสิ่งที่รู้อยู่แล้วทันที — ช่องค้นหาที่พิมพ์ได้เลย ตัวกรอง หัวการ์ด และ
**หัวตารางจริง** — แล้วเติมเฉพาะแถวข้อมูลทีหลัง (`components/Skeleton.js`)

ต่างจากการขึ้นคำว่า "กำลังโหลด…" ตรงที่ผู้ใช้เห็นตั้งแต่แรกว่าหน้านี้มีอะไรและอยู่ตรงไหน
และเนื้อหาไม่กระโดดตอนข้อมูลมาถึง เพราะโครงจองพื้นที่ไว้ให้ในขนาดเดียวกันแล้ว
ผู้ที่ตั้งค่าระบบให้ลดการเคลื่อนไหวจะไม่เห็นแอนิเมชัน และโปรแกรมอ่านหน้าจอจะได้ยิน
ข้อความบอกสถานะแทน

### 2. ตัวเลขหน้าแรกคำนวณไว้ล่วงหน้า อัปเดตวันละครั้ง

หน้าภาพรวมต้องกวาดทั้ง `items` / `vendors` / `transactions` (~195,000 แถว) ซึ่งให้คำตอบ
เดิมทั้งวัน เพราะข้อมูลต้นทางเปลี่ยนเฉพาะตอนรัน ETL จึงคำนวณครั้งเดียวแล้วเก็บผลไว้ที่
**`app_snapshots`** แล้วอ่านซ้ำจากที่นั่น (`services/snapshot.py`)

| | |
|---|---|
| อายุข้อมูล | `SNAPSHOT_TTL_HOURS` ใน `.env` (ค่าเริ่มต้น 24 ชั่วโมง) |
| วอร์มตอนเปิดเซิร์ฟเวอร์ | ทำเบื้องหลัง ไม่ทำให้ startup ช้า — คนแรกที่เข้าเว็บได้ของพร้อมใช้ |
| ถ้าหมดอายุพอดี | ผู้ใช้ได้ของเก่าไปใช้ก่อนทันที ไม่ต้องรอคนอื่นคำนวณเสร็จ |
| คำนวณพร้อมกันหลายคน | กันด้วย lock — คำนวณจริงแค่ครั้งเดียว |
| อยากอัปเดตทันที | กดปุ่ม "คำนวณใหม่ตอนนี้" บนหน้าภาพรวม หรือ `POST /api/catalog/overview/refresh` |

หน้าภาพรวมมีแถบบอกว่า **ตัวเลขนี้คำนวณไว้เมื่อไร** เพื่อไม่ให้เข้าใจผิดว่าเป็นข้อมูลสด ๆ
และ `/api/health` รายงานอายุกับเวลาที่ใช้คำนวณของข้อมูลสรุปทุกชุด

> หลังรัน ETL รอบใหม่ ให้กด "คำนวณใหม่ตอนนี้" ถ้าไม่อยากรอรอบอัปเดตประจำวัน

## API หลัก

| Endpoint | ทำอะไร |
|---|---|
| `GET /api/catalog/items` | ค้นหาสินค้า (q, class_id, vendor_id, single_source, price_volatile, has_price, sort) |
| `GET /api/catalog/items/{part_num}` | รายละเอียด + ราคาล่าสุด/ต่ำสุด/สูงสุด + ผู้ขายทุกราย |
| `GET /api/catalog/items/{part_num}/transactions` | รายการเคลื่อนไหว (กรองด้วย doc_type) |
| `GET /api/catalog/items/{part_num}/price-history` | จุดราคาทุกครั้งที่ซื้อ ไว้วาดกราฟ |
| `GET /api/catalog/items/{part_num}/vendors` | ผู้ขายที่เคยขายรหัสนี้ |
| `GET /api/catalog/overview` | ตัวเลขสรุปหน้าภาพรวม (อ่านจากที่คำนวณไว้) |
| `POST /api/catalog/overview/refresh` | สั่งคำนวณข้อมูลสรุปใหม่ทันที |
| `GET /api/vendors` | รายชื่อผู้ขาย |
| `GET /api/vendors/{key}` · `/items` · `/transactions` · `/contacts` | รายละเอียดผู้ขาย |
| `GET /api/vendors/{key}/deliveries` | ประวัติการส่งรายงวด (only_late / only_overdue / only_rescheduled) |
| `GET /api/vendors?otd_max=70&reliable_only=true` | กรองผู้ขายที่ส่งตรงเวลาต่ำกว่าเกณฑ์ |
| `GET /api/deliveries` | งวดส่งของข้ามผู้ขายทั้งหมด (q, only_late, only_on_time, only_overdue, only_rescheduled, min_days_late) |
| `GET /api/deliveries/by-vendor` | สรุปงวดแยกรายผู้ขาย พร้อมตัวอย่าง 5 งวด |
| `GET /api/deliveries/summary` | ตัวเลขสรุปการส่งของทั้งบริษัท |
| `POST /api/boms/parse` · `/parse-file` | อ่าน BOM จากข้อความหรือไฟล์ Excel/CSV (ยังไม่บันทึก) |
| `POST /api/boms` | สร้างงานประมาณราคา + จับคู่สินค้าให้อัตโนมัติ |
| `GET /api/boms/{id}` | รายการ + ราคา + ยอดรวมพร้อมความครอบคลุม |
| `GET /api/boms/{id}/lines/{no}/candidates` | สินค้าที่ใกล้เคียงของบรรทัดนั้น (ใช้ตอนคลิกแก้รายตัว) |
| `PATCH /api/boms/{id}/lines/{no}` | เปลี่ยนสินค้าที่จับคู่ / แก้จำนวน / กรอกราคาเอง |
| `POST /api/boms/{id}/rematch` | จับคู่ใหม่ทั้งใบ (ข้ามบรรทัดที่คนเลือกเอง) |
| `GET /api/boms/{id}/rfq-plan` | รายการที่ออกใบได้ + ผู้ขายที่เคยขายรหัสนั้น (ราคา + OTD) |
| `GET /api/boms/{id}/lines/{no}/vendor-search` | ค้นผู้ขายเพิ่ม · `by=name` ตามชื่อ · `by=item` ตามอุปกรณ์ใกล้เคียง |
| `POST /api/boms/{id}/rfqs` | ออกใบขอราคาจากรายการที่เลือก · `group_by=vendor` ใบเดียวต่อผู้ขาย · `group_by=item` ใบเดียวต่อรายการ |
| `POST /api/boms/{id}/rfq` | ออกใบขอราคา **รวมทุกรายการไว้ใบเดียว** |
| `GET /api/boms/{id}/comparison` | เทียบราคาทั้งโครงการ แถวละสินค้า คอลัมน์ละผู้ขาย |
| `POST /api/boms/{id}/award` | เลือกผู้ชนะรายสินค้า (ระบบหาใบขอราคาที่ถูกต้องให้เอง) |
| `GET /api/boms/{id}/export` | โหลดงบประมาณเป็นไฟล์ Excel |
| `POST /api/rfqs` | สร้าง RFQ (`lines: [{part_num, qty}]`, `vendor_keys`) |
| `GET /api/rfqs/{id}/suggested-vendors` | ผู้ขายที่เคยขายรหัสเหล่านี้ให้เรา |
| `POST /api/rfqs/{id}/send` | ออกใบขอราคา + ลิงก์ portal |
| `GET /api/rfqs/{id}/comparison` | ตารางเทียบราคา (มี `last_price` และ `saving_vs_last_price`) |
| `POST /api/rfqs/{id}/award` | ประกาศผู้ชนะ |
| `GET /api/portal/{token}` | หน้าผู้ขาย (ไม่ต้องล็อกอิน) — ก่อนรับทราบเงื่อนไขจะยังไม่ส่งรายการสินค้าออกไป |
| `POST /api/portal/{token}/accept-terms` | บันทึกการรับทราบเงื่อนไข (ต้องทำก่อนจึงเสนอราคาได้) |
| `POST /api/portal/{token}/attachments` | แนบไฟล์ใบเสนอราคาของผู้ขาย (เก็บลง MongoDB) |
| `GET /api/portal/{token}/attachments/{file_id}` | ผู้ขายเปิดไฟล์ที่ตัวเองแนบ (เฉพาะของตัวเอง) |
| `GET /api/files/{file_id}` | ดาวน์โหลดไฟล์ — ต้องล็อกอิน |
| `GET /api/boms?trash=true` | ถังขยะของตัวเอง · `mine=true` = เฉพาะที่ตัวเองสร้าง/ถูกเพิ่ม |
| `DELETE /api/boms/{id}` | ย้ายโครงการเข้าถังขยะ (เจ้าของ/admin) |
| `POST /api/boms/{id}/restore` | กู้คืนจากถังขยะ |
| `DELETE /api/boms/{id}/purge` | ลบถาวร — admin และต้องอยู่ในถังขยะก่อน |
| `POST /api/boms/{id}/assignees` | เพิ่ม/ถอดคนเข้าออกจากโครงการ |
| `DELETE /api/rfqs/{id}` | ยกเลิกใบขอราคา — เพิกถอนลิงก์ของผู้ขายทันที |
| `POST /api/rfqs/{id}/restore` | กู้ใบที่ยกเลิกไว้ ลิงก์ใช้ได้อีกครั้ง |
| `POST /api/rfqs/bulk-cancel` | ยกเลิกหลายใบที่ติ๊กเลือก — รายงานใบที่ข้ามพร้อมเหตุผล |
| `POST /api/rfqs/bulk-restore` | กู้หลายใบที่ติ๊กเลือก |
| `GET /api/rfqs?trash=true` | ใบที่ยกเลิกไว้ |
| `GET /api/users/meta/departments` | รายชื่อหน่วยงานที่มีอยู่ (ใช้เป็นตัวเลือก) |
| `GET /api/health` | สถานะ + จำนวนข้อมูลแต่ละ collection + `etl_ready` |

`vendor_key` มีรูปแบบ `epicor:<vendorId>` แต่ส่งรหัสผู้ขายเปล่า ๆ มาก็รับ
(ลิงก์เก่าจึงไม่พัง)

โค้ดชุดเก่าที่เลิกใช้ (นำเข้า Partner Contact.xlsx, จับคู่ผู้ขายด้วยหมวด, BOM เดิม)
ถูกย้ายออกไปไว้ที่ `_to_delete\` ที่รากโปรเจกต์แล้ว ไม่ได้อยู่ปนกับโค้ดที่ใช้จริงอีก —
ตรวจแล้วลบทั้งโฟลเดอร์ได้เลย

## ส่วนขยายของเบราว์เซอร์กับ hydration

`<html>` และ `<body>` ตั้ง `suppressHydrationWarning` ไว้ เพราะส่วนขยายอย่าง QuillBot
(`data-qb-installed`), Grammarly (`data-gr-ext-installed`) หรือตัวแปลภาษา
เขียน attribute ลงบนสองแท็กนี้ **ก่อน** React จะ hydrate ฝั่งเซิร์ฟเวอร์ไม่มี attribute พวกนั้น
React จึงฟ้อง hydration mismatch ทั้งที่แอปไม่ได้ทำอะไรผิด และ dev overlay ที่ขึ้นทับทุกครั้ง
จะบัง error จริงที่ควรเห็น

ปิดเสียงเฉพาะ **attribute ของสองแท็กนี้** เท่านั้น ไม่ได้ปิดทั้งต้นไม้ —
hydration mismatch ที่เกิดในหน้าจริง (เช่นเคส `<tbody>` ซ้อนกันที่เคยเจอ) ยังฟ้องตามปกติ

## เปิดให้เข้าจากภายนอกผ่าน ngrok

เปิดทะลุที่ **frontend (พอร์ต 3000)** เท่านั้น — Next ส่งต่อ `/api` ไปหลังบ้านให้อยู่แล้ว
ถ้าเปิดทะลุไปที่ backend ตรง ๆ จะได้แต่ API ไม่มีหน้าเว็บ

```powershell
ngrok http 3000 --domain=ชื่อโดเมนของคุณ.ngrok-free.dev   # อีกหน้าต่างหนึ่ง
.\run-ngrok.ps1                                          # เติมค่าให้ครบทุกที่
```

`run-ngrok.ps1` อ่าน URL จาก ngrok ที่เปิดอยู่ (`http://127.0.0.1:4040/api/tunnels`)
แล้วเติมค่าให้ทั้งสี่ที่ที่ต้องตรงกัน — พลาดที่เดียวก็ล็อกอินไม่ได้ และอาการที่ได้
ไม่ได้บอกว่าพลาดตรงไหน:

| ตั้งที่ | ค่า | ถ้าไม่ตั้งจะเป็นยังไง |
|---|---|---|
| `.env` `FRONTEND_URL` | URL ของ ngrok | ลิงก์ที่ส่งให้ผู้ขายชี้ไป localhost — ผู้ขายเปิดไม่ได้ |
| `.env` `CORS_ORIGINS` | localhost + ngrok | เบราว์เซอร์บล็อกคำขอข้ามโดเมน |
| `.env` `MS_REDIRECT_URI` | `<ngrok>/api/auth/ms/callback` | ล็อกอิน Microsoft ขึ้น AADSTS50011 |
| `.env` `COOKIE_SECURE` | `true` | คุกกี้ session ไม่ถูกส่งกลับบน https |
| `frontend\.env.local` `DEV_ORIGINS` | โฮสต์ของ ngrok | Next โหมด dev บล็อกคำขอจากโดเมนอื่นทิ้ง |

เลิกใช้แล้วกลับมาเป็น localhost: `.\run-ngrok.ps1 -Revert`

**อีกสองอย่างที่ต้องทำเอง**

1. **Azure Portal → App registrations → Authentication → Web → Redirect URIs**
   เพิ่ม `<ngrok>/api/auth/ms/callback` ให้ตรงเป๊ะ (ห้ามมี `/` ปิดท้าย, path เป็น case-sensitive)
2. **รีสตาร์ท backend และ `next dev`** — ทั้งคู่อ่านค่าพวกนี้ตอนสตาร์ทครั้งเดียว

**สองอย่างที่แก้ไว้ในโค้ดแล้ว ไม่ต้องทำเอง**

- ทุกคำขอ API ติดหัวข้อมูล `ngrok-skip-browser-warning` — ngrok รุ่นฟรีจะขั้นหน้าเตือน
  "You are about to visit…" กับคำขอที่มาจากเบราว์เซอร์ **รวมถึง `fetch` ของหน้าเว็บด้วย**
  ผลคือ API คืน HTML แทน JSON แล้วหน้าจอขึ้น error ที่ไล่ต้นเหตุไม่ถูกเลย
  (ตอนผู้ขายเปิดลิงก์ครั้งแรกยังเจอหน้านี้หนึ่งครั้ง กด Visit Site ได้เลย —
  หน้าเตือนของการเปิดหน้าเว็บตรง ๆ ข้ามด้วยหัวข้อมูลไม่ได้)
- `next.config.mjs` อนุญาตโดเมน ngrok ทุกแบบ (`*.ngrok-free.app`, `*.ngrok-free.dev`,
  `*.ngrok.app`, `*.ngrok.io`, `*.ngrok.dev`) ไว้ให้แล้วสำหรับโหมด dev

> **แนะนำให้ใช้ static domain ของ ngrok** (บัญชีฟรีได้ 1 โดเมน) —
> URL แบบสุ่มจะเปลี่ยนทุกครั้งที่เปิด ngrok ใหม่ แปลว่าต้องรัน `run-ngrok.ps1`
> และไปเพิ่ม Redirect URI ใน Azure ใหม่ทุกครั้ง ซึ่งลืมง่ายมาก

## ใครเห็นโครงการไหน — หน่วยงานและการมอบหมาย

**ผู้ขาย สินค้า ราคาที่เคยซื้อ และรายการซื้อขายทั้งหมด ทุกคนยังเห็นได้เหมือนเดิม**
ข้อจำกัดนี้ใช้กับ *โครงการ* (งานประมาณราคา BOM) เท่านั้น

เห็นโครงการได้เมื่อเข้าเงื่อนไขข้อใดข้อหนึ่ง:

1. เป็นคนสร้างเอง
2. โครงการนั้นเป็นของหน่วยงานที่ตัวเองสังกัด
3. ถูกเพิ่มเข้าโครงการนั้นเป็นรายคน (ใช้กับคนนอกหน่วยงาน)

admin เห็นทุกโครงการ

**หน่วยงาน** admin เป็นคนกำหนดให้แต่ละคนที่หน้า `/admin/users` · คนเดียวสังกัดได้หลายหน่วยงาน
(คั่นด้วยจุลภาค) และ **หน่วยงานแรกคือค่าตั้งต้น** ตอนคนนั้นสร้างโครงการใหม่ —
ถ้าอยู่หลายหน่วยงาน ตอนสร้างโครงการจะมีให้เลือกว่าโครงการนี้เป็นของหน่วยงานไหน

| ทำอะไรได้ | เจ้าของโครงการ | คนในหน่วยงานเดียวกัน | คนที่ถูกเพิ่มเข้าโครงการ | admin |
|---|:--:|:--:|:--:|:--:|
| เปิดดู / แก้รายการ / ออกใบขอราคา | ✓ | ✓ | ✓ | ✓ |
| เปลี่ยนหน่วยงานเจ้าของ · เพิ่ม-ถอดคน | ✓ | — | — | ✓ |
| ลบเข้าถังขยะ / กู้คืน | ✓ | — | — | ✓ |
| ลบถาวร | — | — | — | ✓ |

**ตรวจที่ฐานข้อมูล ไม่ใช่ที่หน้าจอ** — เงื่อนไขถูกใส่เข้าไปในคำสั่งค้นตั้งแต่ต้น
และทุกเส้นทางที่แตะโครงการผ่านฟังก์ชันเดียวกัน (`_get_or_404`) ที่ตรวจสิทธิ์ให้เสร็จในตัว
ถ้าแยกกันตรวจทีละเส้นทาง เดี๋ยวจะมีสักเส้นทางที่ลืมตรวจแล้วข้อมูลหลุดโดยไม่มีใครสังเกต

**ใบขอราคาที่ออกจากโครงการก็ถูกจำกัดตามโครงการด้วย** — ถ้าไม่ทำ ชื่อโครงการกับราคา
จะไปโผล่ในหน้ารายการใบขอราคาให้คนที่ไม่มีสิทธิ์เห็นโครงการนั้นอยู่ดี
ส่วนใบที่ขอราคาจากหน้าสินค้าตรง ๆ (ไม่ผูกโครงการ) ทุกคนยังเห็นได้เหมือนเดิม

**ข้อความตอนถูกปฏิเสธบอกทางออกด้วย** ไม่ใช่แค่ "ไม่มีสิทธิ์" —
บอกว่าเป็นของหน่วยงานไหนและให้ขอเจ้าของเพิ่มเข้าโครงการ ไม่งั้นคนที่ได้ลิงก์มาจาก
เพื่อนร่วมงานจะนึกว่าโครงการถูกลบไปแล้ว แล้วไปสร้างใหม่ซ้ำ

### ลบโครงการ = ย้ายเข้าถังขยะ (และใบขอราคาถูกยกเลิกไปด้วย)

ลบแล้วหายจากทุกหน้าจอทันที แต่ **ไม่ได้ลบออกจากฐานข้อมูลจริง** — กู้คืนได้จากแท็บถังขยะ
เหตุผลที่ไม่ลบทันที: โครงการที่ออกใบขอราคาไปแล้วมีผู้ขายถือใบอยู่ข้างนอก
ลบถาวรทีเดียวคือเสียประวัติที่ตามกลับไม่ได้

- ถังขยะเป็นของใครของมัน — คนในหน่วยงานไม่เห็นของที่คนอื่นลบ
- ลบถาวรทำได้เฉพาะ admin และ **ต้องอยู่ในถังขยะก่อน** กันการกดพลาดครั้งเดียวแล้วหายถาวร

**ใบขอราคาที่ออกจากโครงการถูกยกเลิกพร้อมกัน** ไม่ปล่อยลอยค้าง — ถ้าปล่อยไว้
ผู้ขายที่ถือลิงก์อยู่จะยังกรอกราคาส่งเข้ามาให้โครงการที่ถูกลบแล้วได้ และคนจัดซื้อ
จะไปเจอใบเสนอราคาของงานที่ยกเลิกไปแล้วปนอยู่ในระบบ

| สิ่งที่เกิดขึ้น | ตอนลบเข้าถังขยะ | ตอนกู้คืน | ตอนลบถาวร (admin) |
|---|---|---|---|
| โครงการ | ซ่อน | กลับมา | ลบออกจากฐานข้อมูล |
| ใบขอราคาของโครงการ | ยกเลิก (ติดธง `deleted_with_bom`) | กลับมาทุกใบ | ลบทิ้ง |
| ผู้ถูกเชิญ / ใบเสนอราคา | คงอยู่ | คงอยู่ | ลบทิ้ง |
| ไฟล์แนบใน MongoDB | คงอยู่ | คงอยู่ | ลบทิ้ง (คืนจำนวนที่ลบมาให้ตรวจ) |
| ลิงก์ของผู้ขาย | เปิดได้ แต่ขึ้นว่า **"ใบขอราคานี้ถูกยกเลิกแล้ว"** | ใช้ต่อได้ตามปกติ | ใช้ไม่ได้ (404) |

ที่กู้คืนแล้วใบกลับมาครบ เพราะตอนยกเลิกติดธง `deleted_with_bom` ไว้ —
กู้เฉพาะใบที่หายไปเพราะโครงการนี้ ไม่ใช่กู้ทุกใบที่เคยถูกลบ

**ฝั่งผู้ขายไม่เจอหน้า error** — เห็นหน้าที่บอกว่ายกเลิกแล้ว พร้อมเลขที่ใบไว้อ้างอิง
ตอนโทรถาม และเซิร์ฟเวอร์ปฏิเสธการส่งราคา/แนบไฟล์/โหลดไฟล์ใบขอราคาทั้งหมด (410 Gone)
ไม่ใช่แค่ซ่อนปุ่มบนหน้าจอ

### ยกเลิกใบขอราคาใบเดียว (ไม่ต้องลบโครงการ)

ปุ่ม **"ยกเลิกใบนี้"** อยู่ที่หัวหน้าใบขอราคา — ใช้ตอนออกใบผิด เลือกผู้ขายผิด
หรือเปลี่ยนใจ โดยที่โครงการยังเดินต่อ

- **ตัดลิงก์ของผู้ขายทุกรายทันที** — เปิดลิงก์เดิมจะเห็นว่า "ใบขอราคานี้ถูกยกเลิกแล้ว"
- ใบหายจากรายการ ไปอยู่ในโหมด **"ยกเลิกแล้ว"** (`/api/rfqs?trash=true`) กู้กลับมาได้
  กู้แล้วลิงก์ของผู้ขายใช้ได้อีกครั้ง และสถานะกลับไปเป็น `sent` ถ้าเคยส่งไปแล้ว
- ใครยกเลิกได้: ใบที่ออกจากโครงการ = เจ้าของโครงการหรือ admin ·
  ใบที่ขอราคาตรงจากหน้าสินค้า = คนที่ออกใบเอง หรือ admin

**ยกเลิกหลายใบพร้อมกัน** — ติ๊กช่องหน้าแถวในหน้ารายการ (ติ๊กที่หัวตาราง = เลือกทุกแถว
ที่กำลังแสดงอยู่) แล้วกดยกเลิกทีเดียว · ในโหมด "ยกเลิกแล้ว" ปุ่มเดียวกันเปลี่ยนเป็นกู้คืน

- ทำงานทีละใบเหมือนกดเอง — ใบที่ไม่มีสิทธิ์หรือยกเลิกอยู่แล้ว **ถูกข้ามและรายงานเหตุผล**
  ไม่ล้มทั้งชุดเพราะใบเดียว และไม่ข้ามแบบเงียบ ๆ แล้วรายงานว่าสำเร็จหมด
- ส่งเป็น "รายการ id ที่ติ๊กไว้" ไม่ใช่คำสั่ง "ยกเลิกทั้งหมดที่ค้นเจอ" — คำสั่งแบบหลัง
  จะกวาดใบที่ไม่ได้อยู่บนหน้าจอตอนนั้นไปด้วย คนกดไม่มีทางรู้ว่ายกเลิกอะไรไปกี่ใบ
- ที่ติ๊กไว้จะถูกล้างทุกครั้งที่เปลี่ยนคำค้น/สลับโหมด และหลังทำเสร็จ
  ไม่ค้างไว้ให้กดซ้ำโดยไม่ตั้งใจ

**ใบที่คนตั้งใจยกเลิกเอง จะไม่ถูกลากกลับมาตอนกู้โครงการ** — ตอนยกเลิกเองติดธง
`deleted_with_bom=false` ไว้ ต่างจากใบที่หายไปเพราะโครงการถูกลบ (`true`)
ถ้าไม่แยกสองกรณีนี้ การกู้โครงการจะพาใบที่ตั้งใจยกเลิกกลับมาด้วย
แล้วผู้ขายที่ถูกบอกไปแล้วว่ายกเลิกจะได้ลิงก์ที่ใช้ได้อีกครั้งโดยไม่มีใครตั้งใจ

> **หลังอัปเดตครั้งแรก:** โครงการเดิมทั้งหมดยังไม่มีหน่วยงาน จึงจะเห็นได้เฉพาะคนที่สร้าง
> กับ admin เท่านั้น (ระบบเลือกทางที่ปลอดภัยไว้ก่อน) เจ้าของโครงการเข้าไปตั้งหน่วยงาน
> ได้ที่แถบบนสุดของหน้าโครงการ แล้วคนในหน่วยงานนั้นจะเห็นทันที

## ไฟล์เก็บที่ไหน — อยู่ใน MongoDB ไม่ใช่ดิสก์

ไฟล์ทุกชนิดในระบบ (ใบเสนอราคาที่ผู้ขายแนบมา, ใบขอราคา Excel ที่ระบบสร้าง)
เก็บอยู่ในฐานข้อมูลเดียวกับข้อมูลอื่น ไม่มีโฟลเดอร์ `uploads` ให้ดูแลอีกแล้ว

| collection | เก็บอะไร |
|---|---|
| `app_files` | ข้อมูลกำกับไฟล์ 1 เอกสาร = 1 ไฟล์ — ชื่อ ขนาด ชนิด sha256 เจ้าของ |
| `app_file_chunks` | เนื้อไฟล์ ตัดเป็นก้อนละ 1 MB `{file_id, n, data}` |

**ทำไมย้าย**

- สำรองข้อมูลครั้งเดียวได้ครบ ย้ายเครื่องไม่ต้องคัดลอกโฟลเดอร์ตามไปด้วย
  และหมดกรณี "แถวในฐานข้อมูลมีอยู่ แต่ไฟล์บนดิสก์หายไปแล้ว"
- **ปิดรูที่ไฟล์เคยเปิดสาธารณะ** — ของเดิม `uploads` ถูก mount เป็น static ที่ `/files`
  ใครเดา URL ถูกก็โหลดใบเสนอราคาของผู้ขายได้โดยไม่ต้องล็อกอิน
  ตอนนี้ต้องผ่าน `/api/files/<id>` ที่ตรวจสิทธิ์ หรือลิงก์ที่ผูกกับ token ของผู้ขายรายนั้น
  (ตรวจด้วยว่าไฟล์นั้นอยู่ในใบเสนอราคาของเขาจริง — เดา id ถูกก็เปิดของคู่แข่งไม่ได้)
- **ลบแล้วหายจริง** — เดิมลบไฟล์แนบออกจากใบเสนอราคา ตัวไฟล์ยังกองบนดิสก์ตลอดไป

**ระหว่างทางที่แก้ไปด้วย:** ฝั่งผู้ซื้อเคยเห็นแค่ "มีไฟล์แนบ 2 ไฟล์" แต่ไม่มีทางเปิดดู
ตอนนี้ตารางเทียบราคามีลิงก์โหลดไฟล์จริงใต้ชื่อผู้ขายแต่ละราย

**สามอย่างที่ระวังไว้ในโค้ด**

1. เขียนก้อนเนื้อไฟล์ให้ครบก่อน แล้วค่อยเขียนเอกสารกำกับเป็นอันสุดท้าย —
   ไฟดับกลางทางจะเหลือแค่ก้อนกำพร้า ไม่ใช่ไฟล์ที่ "มีชื่อในระบบแต่เนื้อไม่ครบ"
   ซึ่งอันตรายกว่ามาก เพราะใบเสนอราคาที่ขาดหน้าท้ายมักเปิดได้ตามปกติ คนอ่านไม่รู้เลยว่าขาด
2. ตอนอ่านกลับ ตรวจจำนวนก้อนกับขนาดทุกครั้ง ไม่ตรงคือ error ไม่ใช่คืนไฟล์ที่ขาดไป
3. ชื่อไฟล์ภาษาไทยส่งกลับด้วย `filename*=UTF-8''` คู่กับชื่อ ASCII —
   ถ้าใส่ชื่อไทยดิบ ๆ ใน header ผู้ขายบางรายจะโหลดไม่ได้เลย

ที่ไม่ใช้ GridFS ของ pymongo ตรง ๆ เพราะชุดทดสอบรันบน mongomock ซึ่งไม่รองรับ GridFS
ถ้าใช้ ส่วนรับ-ส่งไฟล์ทั้งหมดจะกลายเป็นส่วนเดียวของระบบที่ไม่มีเทสต์ครอบเลย
รูปแบบที่เก็บจึงทำให้เหมือน GridFS (files + chunks) ไว้ ย้ายไปใช้ของจริงทีหลังได้

### ย้ายไฟล์เก่าที่ยังอยู่บนดิสก์

```powershell
cd backend
..\.venv\Scripts\python scripts\migrate_uploads_to_mongo.py            # ดูก่อนว่าจะย้ายอะไร
..\.venv\Scripts\python scripts\migrate_uploads_to_mongo.py --commit   # ย้ายจริง
```

ย้ายเฉพาะไฟล์แนบของผู้ขาย เพราะเป็นไฟล์เดียวที่สร้างใหม่ไม่ได้ —
ใบขอราคา/งบประมาณที่เป็น Excel ระบบสร้างใหม่ให้เองเมื่อมีคนกดโหลด
สคริปต์ไม่ลบไฟล์ต้นทาง ตรวจว่าโหลดครบแล้วค่อยลบโฟลเดอร์ `uploads` เอง

## เก็บเข้า git อะไรบ้าง

`.gitignore` อยู่ที่รากโปรเจกต์ ยึดหลักว่า **เก็บเฉพาะสิ่งที่เขียนเอง**
ส่วนของที่สร้างใหม่ได้ (`node_modules/`, `.next/`, `__pycache__/`, `.venv/`)
และของที่เป็นข้อมูลจริง ไม่เข้า repo:

| ไม่เข้า repo | เพราะ |
|---|---|
| `Data/` | ไฟล์ Excel ที่ export จาก Epicor — ข้อมูลราคาและผู้ขายของจริง ใหญ่ และ export ใหม่ได้ |
| `backend/uploads/` | ของเก่าที่รอย้ายเข้าฐานข้อมูล — ไฟล์ใหม่ไม่ลงดิสก์แล้ว (ดูหัวข้อ "ไฟล์เก็บที่ไหน") |
| `.env`, `.env.local` | มีสตริงต่อ MongoDB และ client secret · ไฟล์ `.env.example` ยังเก็บไว้เป็นแบบ |
| `_*.tgz`, `_to_delete*/`, `_old_v*/`, `_removed/` | ของเหลือจากการส่งงานทีละรอบ ไม่ใช่ส่วนหนึ่งของโปรเจกต์ |
| `~$*` | ไฟล์ล็อกที่ Excel สร้างทุกครั้งที่เปิดไฟล์ BOM ค้างไว้ |
| `frontend/_shots/`, `*.pkl` | ภาพหน้าจอกับข้อมูลจำลองที่ชุดทดสอบสร้างขึ้นใหม่ได้ทุกครั้งที่รัน |

ที่ **เก็บ** ไว้แม้จะดูเหมือนไฟล์ชั่วคราว: `samples/` (ไฟล์ BOM ตัวอย่างสำหรับทดสอบ ขนาดเล็ก)
และ `frontend/AGENTS.md` / `frontend/CLAUDE.md` (`next dev` เขียนใหม่ให้ทุกครั้ง —
ถ้า ignore ไว้ มันจะโผล่เป็นไฟล์ใหม่ทุกเครื่องที่รัน commit ไปเลยจบกว่า)

`.gitattributes` บังคับ `text=auto` เพราะทีมทำงานบน Windows — ถ้าไม่ตั้งไว้
git จะมองว่าไฟล์ทั้งไฟล์เปลี่ยนทั้งที่เปลี่ยนแค่ตัวจบบรรทัด แล้ว diff จะอ่านไม่รู้เรื่อง

> **ถ้าเคยรัน `create-next-app` แล้วมีโฟลเดอร์ `frontend\.git` ค้างอยู่ ให้ลบทิ้งก่อน
> `git init` ที่ราก** — repo ซ้อน repo ที่ยังไม่มี commit จะทำให้ `git add` ที่รากล้ม
> ทั้งคำสั่งด้วย `error: 'frontend/' does not have a commit checked out`
> แล้วโค้ดฝั่งหน้าเว็บทั้งหมดจะไม่เข้า repo เลย (ตอนนี้ในเครื่องยังไม่มี ตรวจแล้ว)

### วิธีรันชุดทดสอบ

ทุกชุดยิงไปที่ **เซิร์ฟเวอร์ทดสอบ** ซึ่งรันโค้ด backend ตัวจริงทุกบรรทัด
แต่เปลี่ยนปลายทางเป็น mongomock — ฐานข้อมูลจริงไม่ถูกแตะเลยแม้แต่ครั้งเดียว

```powershell
# 1. สร้างข้อมูลจำลอง (ทำครั้งเดียว)
cd backend
$env:DUMP_ONLY = "1"; python tests\seed_epicor.py

# 2. เปิดเซิร์ฟเวอร์ทดสอบไว้อีกหน้าต่าง (พอร์ต 8000)
python tests\testserver.py

# 3. ขอโทเคนของผู้ใช้ทดสอบ
curl -X POST "http://127.0.0.1:8000/api/auth/token?email=buyer@precise.co.th"
#    เอาค่า access_token ไปใส่ตัวแปร TEST_TOKEN หรือเขียนลงไฟล์ที่ TEST_TOKEN_FILE ชี้ไว้

# 4. ชุด API
python tests\api_check.py
python tests\access_check.py

# 5. ชุดหน้าเว็บ — ต้อง build แล้วเปิดที่พอร์ต 3100 ก่อน
cd ..\frontend
npx next build; npx next start -p 3100
node e2e_check.mjs        # และ bom_ portal_ askmore_ skeleton_ theme_ proxy_ access_ui_ hydration_
```

ค่าที่ปรับได้ด้วย environment variable (ไม่ตั้งก็ใช้ค่าเริ่มต้นด้านบน):

| ตัวแปร | ค่าเริ่มต้น | ใช้ทำอะไร |
|---|---|---|
| `TEST_API` | `http://127.0.0.1:8000/api` | ที่อยู่ API ที่จะยิงไป |
| `TEST_FRONTEND` | `http://localhost:3100` | ที่อยู่หน้าเว็บที่จะเปิด |
| `TEST_TOKEN` / `TEST_TOKEN_FILE` | — / `/tmp/tok` | โทเคนของผู้ใช้ทดสอบ |
| `TEST_CHROMIUM` | `/opt/pw-browsers/chromium` | ที่อยู่เบราว์เซอร์ของ Playwright |
| `TEST_SHOTS` | `frontend/_shots/` | ที่เก็บภาพหน้าจอที่ถ่ายระหว่างรัน |
| `TEST_SEED` | `/tmp/epicor_seed.pkl` | ไฟล์ข้อมูลจำลองที่ `testserver.py` โหลด |
| `TEST_PORT` | `8000` | พอร์ตของเซิร์ฟเวอร์ทดสอบ |

ที่อยู่พวกนี้เคยถูกฝังตายไว้ในไฟล์ทดสอบทุกไฟล์ ทำให้ชุดทดสอบรันได้เฉพาะบนเครื่อง
ที่เขียนมันขึ้นมาเท่านั้น ตอนนี้อ่านจาก `backend/tests/_env.py` กับ `frontend/_env.mjs`
ที่เดียว
